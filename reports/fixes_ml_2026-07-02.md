## FIX 1 — Vega 100× scale mismatch between numba_greeks and bs_greeks

**Files changed:** `backend/services/numba_greeks.py`

**Root cause:** `bs_vega_vec` divided the raw Black-Scholes vega by 100 before returning, producing values like 0.054 instead of 5.43. `bs_greeks.bs_vega` returned the raw value (no division). This 100× discrepancy made GEX/VEX dollar-exposure calculations wrong whenever the numba path was used as a fallback.

**Convention confirmed:** The platform-wide standard (pinned in `bs_greeks.py` docstring and `test_greek_scalers.py`) is that `vega` is the raw Black-Scholes value per 1-unit IV change. The "per 1% vol move" scaling (`× 0.01`) is applied downstream by `dollar_vega_per_contract`. Both `bs_greeks.bs_vomma` and the test canonical value (≈ 5.43 for Hull Table 15.1 ATM call) confirm the no-division convention.

**Changes:**
- `bs_vega_vec`: Removed `/ 100.0` from the return line.
- `bs_vomma_vec`: Removed `/ 100.0` from the internal `vega_i` intermediate (which was also wrong for the same reason).

**Compensating factors:** None found in `greek_aggregator.py` or `gex_aggregator.py`.

## FIX 2 — Double-counted slippage in backtest engine

**File changed:** `backend/services/backtest/engine.py`

**Root cause:** Slippage was charged twice per trade leg:
1. **Entry** — `entry_price = close * (1 + slip_pct)` embeds slippage in the fill price, AND `slippage_cost` was added separately to `cost`, so equity was debited `slip × qty` twice at open.
2. **Exit** — `gross_pnl = (exit_price - entry_price) × qty` already captures both legs' slippage (since both prices are slip-adjusted), AND `entry_slippage + slippage_cost` were subtracted again from `net_pnl`.

**Changes:**
- **BUY_CALL / BUY_PUT**: Removed `+ slippage_cost` from the `cost` deducted from equity. `entry_price` already reflects the slippage paid.
- **SELL_CALL / SELL_PUT / forced-close block**: Changed `net_pnl` to `gross_pnl - entry_commission - commission_cost` (removed `- entry_slippage - slippage_cost`). `gross_pnl` already captures slippage via adjusted prices.
- `TradeRecord.slippage` field is still populated with the full entry + exit slippage amount for reporting/audit purposes only — it is no longer deducted from `net_pnl`.

## FIX 3 — Health monitor field name mismatch (completely non-functional)

**File changed:** `backend/services/ml/health_monitor.py`

**Root cause:** All MongoDB queries used the wrong field names. The `ml_predictions` registry stores `"ts"` (not `"timestamp"`) and `"realized_outcome"` (not `"outcome"`). Every query silently returned 0 documents, making the health monitor always report `UNKNOWN` status regardless of model performance.

**Changes (3 locations):**
1. Rolling accuracy loop — find filter: `"timestamp"` → `"ts"`, `"outcome"` → `"realized_outcome"`; doc accessor: `d.get("outcome")` → `d.get("realized_outcome")`
2. Data freshness check — `sort([("timestamp", -1)])` → `sort([("ts", -1)])`; `"timestamp" in latest` → `"ts" in latest`; `latest["timestamp"]` → `latest["ts"]`
3. `_compute_feature_drift` — `.sort("timestamp", -1)` → `.sort("ts", -1)`

## FIX 4 — Missing 5-bar embargo gap in ml_training.py

**File changed:** `backend/ml_training.py`

**Root cause:** The 80/20 temporal train/test split had no embargo gap. Features with multi-bar smoothing windows (rolling means, momentum, etc.) computed at the last training bars bleed into the first test bars, creating indirect look-ahead. Tests confirmed a 5-bar embargo was intended.

**Change in `train_regime_prediction_model`:**
```python
# Before
split_idx = int(len(X) * 0.8)
X_train, X_test = X[:split_idx], X[split_idx:]

# After
split_idx = int(len(X) * 0.8)
embargo_end_idx = min(split_idx + 5, len(X))
X_train, X_test = X[:split_idx], X[embargo_end_idx:]
# (same for y_train, y_test)
```
The 5 embargoed bars are dropped from both train and test; they are never used.

## FIX 5 — Wrong holdout fold in ml_advanced.py walk-forward CV

**File changed:** `backend/ml_advanced.py`

**Root cause:** `train_with_walkforward_cv` selected the model with the **highest test-fold accuracy** as the "best" model for deployment:
```python
if acc > best_accuracy:
    best_accuracy = acc
    best_model = model
    best_scaler = scaler
```
This is data snooping — the test fold's performance is used to select which model to deploy, making the reported `best_accuracy` an optimistic upward-biased estimate. For time series data, the correct holdout is the **last fold** (most future data), which is the most informative for production evaluation.

**Change:** Replaced the `if acc > best_accuracy` conditional with `if _i == n_splits - 1:`, so the model saved for deployment is always the one trained on the temporally-final fold.
