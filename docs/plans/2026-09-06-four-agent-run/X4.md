# X4 — Consumer stability, polling and remount audit (Agent 3 frontend)

## Why

RECOVERY-QUEUE.md agent-3 backlog item 4. Flowseeker Pro components poll backend
endpoints on timers, react to ticker changes, and must handle unmount/abort/stale-response
/empty-response/malformed-row/partial-data correctly. This task audits those stability
behaviors as a consumer: does the mounted component clean up after itself, does it handle
a slow or failed response without crashing or showing garbage, and do multiple pollers
play nicely together?

This builds on QUEUE.md's X2 contract (the same surfaces) but focuses on stability and
lifecycle rather than visual/render correctness. The two tasks are complementary — X2
verifies what renders, X4 verifies that it survives real-world conditions.

## Scope (what this task covers)

### Polling / timer lifecycle
- For each component that polls (feed, chart, tracker, etc.): does it start a timer on
  mount and clear it on unmount? Test that unmount cancels in-flight requests.
- Does a component that re-mounts (e.g. tab switch, drawer open/close) restart cleanly
  without duplicate timers or stale-state leaks?

### Ticker change behavior
- When the ticker changes: does the component abort the previous ticker's in-flight
  request before starting the new one?
- Does the new ticker's response arrive in the correct order (no stale response from the
  previous ticker overwriting the new one)?
- Edge case: rapid ticker changes (user arrows through tickers quickly) — does the
  component keep up without building up a queue of pending requests?

### Stale / slow response handling
- If a response arrives after the component has moved on (ticker changed, component
  unmounted): is it ignored?
- If a response is slow: does the UI show a loading state, a stale indicator, or nothing?
  Does it time out gracefully?

### Empty / error / malformed responses
- Empty response (valid HTTP, empty body / empty array): does the UI show an explicit
  empty state?
- Malformed response (missing expected fields, wrong types): does the component degrade
  gracefully without crashing?
- Error response (5xx, 429, network error): does the component show an error state and
  not blank the whole surface?

### Combined poller interaction
- When multiple components poll the same or related endpoints: do they share a cache, or
  do they fire duplicate requests?
- Verify cost captions (if any) reflect available evidence rather than invented billing
  numbers.

## Exclusions

- No backend changes — this is frontend-only. If a stability issue traces to a backend
  contract (e.g. missing field in response), flag it for the Data lane, don't fix it here.
- No new signal computation — verify the existing consumer survives, don't change what it
  computes.
- No App.js edits unless Agent 1/Nav records a standing waiver.
- No live provider calls — test with fake timers, fake network, and recorded fixtures.
- No browser perf profiling unless a slow path is demonstrated — don't profile without a
  repro.

## Deliverable

A receipt file (X4-receipt.md) containing:

1. **Poller inventory**: list of every component that polls or starts a timer, with the
   endpoint, poll interval (if any), and mount/unmount lifecycle behavior.
2. **Lifecycle test results**: for each poller, the verdict on mount/unmount/abort/ticker-
   change/stale-response/empty-response/malformed-response/error-response. Pass/fail with
   citation to a test or a documented gap.
3. **Combined poller audit**: whether multiple pollers cause duplicate fetches, and whether
   any cache-sharing or dedup is in place.
4. **Gap list**: any lifecycle/stability defect found, with a one-line fix description.
   Each fix is a separate admitted unit.
5. **Blocker list**: any issue that needs a backend contract change or a product decision
   flagged for the appropriate lane.

## Test discipline

- Fake timers (jest.useFakeTimers) and fake network (msw or comparable) for polling/audit
  tests — no real network, no real timers.
- Every new test must fail before the fix and pass after.
- Full-suite green before commit.
- If a scenario can't be tested in node (e.g. it genuinely needs a browser), say so — don't
  fake it.

## Estimated effort

Poller inventory + lifecycle audit: 45–70 minutes depending on how many components poll
and how many gaps are found.

## Code pointers

Start from the X2 surface inventory (same components). Focus on the lifecycle hooks
(useEffect cleanup, abort controllers, timer references) and the response-handling paths
(success → render, empty → state, error → state, malformed → degrade). The existing
`FlowseekerProBlademap.test.jsx` and component-level tests are the baseline; this task
adds lifecycle/stability scenarios on top.
