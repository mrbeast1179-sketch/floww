# ADR-0004 — Deploy CORS headers & exception handler origin echo

**Status:** Accepted
**Date:** 2026-08-31
**Context:** The Confluence Decoder serves a React frontend (same origin or different origin in production via Caddy). The backend must return correct CORS headers on all responses, including error responses (429, 422, 500) which FastAPI's default exception handlers may bypass. This ADR records the decision to echo the runtime-effective CORS origin on every response, including errors.

---

## Decision

All HTTP responses from the backend include these CORS headers:

```http
Access-Control-Allow-Origin: <runtime-effective origin>
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization, X-API-Key
```

The `Access-Control-Allow-Origin` value is determined at request time by `_get_cors_origin_for_handlers()`, which reads the module-level `_cors_origins` list populated by the CORS config block at import time. In production/staging with `CORS_ORIGINS` unset, server startup aborts with `RuntimeError` before any request reaches the handlers (defense-in-depth).

**Exception handlers** (HTTP 400/422/500) explicitly include the CORS headers in their `JSONResponse`:

```python
@app.exception_handler(StarletteHTTPException)
async def http_exception_handler(request: Request, exc: StarletteHTTPException):
    return JSONResponse(
        status_code=exc.status_code,
        content={...},
        headers={
            "Access-Control-Allow-Origin": _get_cors_origin_for_handlers(),
            "Access-Control-Allow-Methods": "GET, POST, OPTIONS",
            "Access-Control-Allow-Headers": "Content-Type, Authorization, X-API-Key",
        },
    )
```

The rate limiter's 429 response also includes CORS headers (via the same `_get_cors_origin_for_handlers()` call).

The `performance_middleware` adds `Cache-Control: no-store, max-age=0` to all `/api/` and `/gex/` responses to prevent browser caching of market data.

## Consequences

### Positive
- Frontend can make cross-origin requests from any environment (dev, staging, production) without CORS errors.
- Error responses (429 rate limit, 422 validation, 500 internal) are accessible to the frontend even when generated by exception handlers that bypass CORSMiddleware.
- Market data is never browser-cached (stale heatmap is worse than slow heatmap).
- Production startup fails fast if CORS_ORIGINS is unset (prevents misconfigured deploys).

### Negative
- The CORS origin is read from a module-level list at import time, not per-request. If the origin needs to change at runtime (e.g., multi-tenant), this would need refactoring.
- The `_get_cors_origin_for_handlers()` helper uses `globals().get("_cors_origins")` for runtime lookup, which is slightly unconventional but survives future refactors of the CORS config block position.

## Alternatives considered

- **FastAPI CORSMiddleware only:** Would handle successful responses but not error responses from exception handlers. Rejected because 429/422/500 errors would be invisible to the frontend.
- **Hardcoded origin:** Would break dev/staging/prod parity. Rejected in favor of env-based origin.
